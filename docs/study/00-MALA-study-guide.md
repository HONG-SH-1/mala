## 1강. 왜 모든 게 10GB에서 시작됐나

### 핵심 개념

GPU 메모리(VRAM)에 올라가는 것은 세 가지다.

**① 가중치 = 파라미터 수 × 파라미터당 비트 ÷ 8**
- FP16은 파라미터당 16비트(2바이트). 8B 모델이면 약 16GB.
- **양자화**는 파라미터 하나를 더 적은 비트로 저장하는 것. 메모리는 줄고 정밀도는 조금 떨어진다.
- MALA의 `qwen3:8b`는 **Q4_K_M**(평균 약 4.8비트), 파라미터 8.2B → 약 4.9GB.

**② KV 캐시**
- 모델은 다음 토큰을 만들 때 앞 토큰들의 중간 계산(Key, Value)을 저장해 다시 계산하지 않는다.
- 크기 ≈ 2(K와 V) × 층 수 × KV 헤드 수 × 헤드 차원 × 바이트 × **토큰 수**
- **컨텍스트 길이에 비례**한다. 가중치는 고정, KV 캐시는 길이에 따라 자란다.
- Qwen3-8B 공개 설정(36층, KV 헤드 8, 헤드 차원 128, FP16) → 토큰당 약 144KB → 4096토큰이면 약 0.56GB.
- KV 헤드가 어텐션 헤드(32개)보다 적은 구조를 GQA라고 한다. KV 캐시를 줄이려는 설계다.

**③ 런타임 오버헤드**
- CUDA 작업 공간, 계산 버퍼 등.

### 실측으로 맞춰 보기

| 측정 | 값 | 무엇을 보여주나 |
|---|---|---|
| `ollama ps` (qwen3:8b, CONTEXT 4096) | 5.6GB | 모델 몫: 가중치 약 4.9 + KV 약 0.56 |
| `nvidia-smi` peak (5월 실측) | 7,559 MiB | GPU 전체: 모델 + CUDA 오버헤드 + 기타 |
| Hermes3-8B `nvidia-smi` peak | 7,418 MiB | — |

두 측정이 다른 이유는 `troubleshooting/2026-05-20-windows-vram-reporting.md`에 있다. **10GB 예산은 `nvidia-smi` 숫자로 짠다.**

### MoE의 함정

- MoE는 토큰마다 일부 전문가만 계산한다 → **연산은 활성 파라미터(예: 3B)만큼**.
- 하지만 어느 전문가가 불릴지 모르니 **전부 메모리에 있어야** 한다 → **메모리는 전체 파라미터(35B)만큼**.
- Qwen 3.6-35B-A3B를 4비트로 해도 약 21GB → 10GB에 불가. **ADR-001**에서 기각.

### MALA에서는

- **ADR-001**: MoE 35B 기각 → Qwen3-8B Q4, Ollama
- **ADR-003**: 두 8B 모델 동시 상주 금지. 7,418 + 7,559 ≈ 15GB > 10GB.

### 🎯 정확히 알아야 할 것

- 활성 파라미터는 **속도**를, 전체 파라미터는 **메모리**를 정한다.
- 7,418/7,559 MiB는 **이미 양자화된 상태**에서 잰 값이다. "양자화하면 되잖아"는 답이 아니다.
- 컨텍스트를 늘리면 **KV 캐시만** 커진다.

### 자가 점검

1-1. Hermes3-8B와 qwen3:8b를 10GB에 동시에 못 올린 이유를 숫자로 설명하라.
1-2. 같은 모델로 컨텍스트만 두 배로 늘리면 무엇이 커지고 무엇이 그대로인가?

## 3강. 에이전트끼리 말하는 법 — 큐와 워커

### 핵심 개념

**왜 큐를 두나 — 세 가지 분리**
- **시간**: 넣는 쪽과 꺼내는 쪽이 다른 때에 움직여도 된다.
- **장애**: 워커가 죽어도 메시지는 남는다.
- **속도**: 몰려도 쌓였다가 순서대로 처리된다.

**Redis 리스트를 큐로**
- `RPUSH`로 넣고 오른쪽에서 꺼낸다 → **FIFO**.
- 앞에 B가 붙은 명령(blocking)은 비어 있으면 메시지가 올 때까지 잠든다 → 놀 때 CPU를 거의 안 쓴다.

**전달 보장 세 단계**

| 보장 | 의미 | 대가 |
|---|---|---|
| 최대 한 번 | 유실 가능, 중복 없음 | 유실 |
| **최소 한 번** | 유실 없음, 중복 가능 | 중복 처리(멱등성) 필요 |
| 정확히 한 번 | 둘 다 없음 | 매우 어렵다 |

- 그냥 `BRPOP`: 꺼내는 순간 큐에서 사라짐 → 처리 중 워커가 죽으면 유실 → **최대 한 번**.
- MALA의 `BRPOPLPUSH`: 꺼내는 동시에 `processing_queue`로 **원자적으로** 옮김 → 워커가 죽어도 남음 → **최소 한 번의 기반**. (Redis 6.2부터는 `BLMOVE`로 이름이 바뀌어 권장된다.)
- 처리가 끝나면 `LREM`으로 처리 큐에서 지운다(ack).
- 처리 불가 메시지는 **DLQ**(dead_letter_queue)로 격리.

**짝짓기 (correlation)**
- 모든 결과가 같은 `result_queue`로 온다 → 꺼낸 쪽이 `task_id`로 "내 답인가"를 확인.

### MALA에서는

```
answer_via_queue ──RPUSH──> [task_queue] ──BRPOPLPUSH──> worker.handle_message
       ▲                                         │
       └──BLPOP── [result_queue] <──RPUSH────────┘
                                   └──> [processing_queue] / [dead_letter_queue]
```

- 계약: `src/schemas/message.py` (TaskEnvelope / ResultEnvelope, pydantic)
- 브로커: `src/broker/redis_queue.py`
- 관측: `src/broker/task_status.py` — 큐와 별도로 Redis Hash에 진행 상황 기록

### 구멍

| 구멍 | 내용 |
|---|---|
| 수동 복구 | `requeue_processing`은 있는데 **호출하는 코드가 없다**. 워커가 죽으면 메시지가 처리 큐에 갇힌다. (상용 큐 예: AWS SQS의 visibility timeout은 이걸 자동으로 한다) |
| A. 남의 답 폐기 | `task_id`가 다른 결과는 로그만 남기고 버린다 → 동시 실행 시 유실. **단일 소비자 전제.** |
| B. 늦은 답 채택 | 재시도해도 `task_id`가 같다 → 1차의 늦은 결과가 2차 답으로 **조용히** 채택된다. |
| 예산 역전 | 워커 최악 약 366초 vs 오케스트레이터 대기 120초(`nodes.py:172` 하드코딩) |
| 늦은 실패 통보 | Envelope가 깨진 경우만 결과를 안 보내고 DLQ에만 넣는다 → 오케스트레이터가 120초를 꽉 기다린다 |

원리: **짝짓는 ID는 "작업"이 아니라 "시도"를 가리켜야 한다.** 그리고 **실패했다는 사실도 메시지다.** 빨리 알릴수록 싸다(fail fast).

### 🎯 정확히 알아야 할 것

- `BRPOPLPUSH`가 "꺼내기 + 옮기기"를 **원자적으로** 하는 이유 = 유실 방지.
- 최소 한 번 전달은 **중복**을 낳는다 → 받는 쪽이 멱등해야 한다.
- MALA는 유실은 막았지만 **자동 재처리는 없다**.

## 4강. 흐름을 지휘하는 법 — LangGraph

### 핵심 개념

- **상태(State)**: 모든 노드가 공유하는 딕셔너리. MALA는 `AgentState`(TypedDict, `total=False`).
- **노드(Node)**: 상태를 받아 **바꿀 부분만** 돌려주는 함수.
- **엣지(Edge)**: 다음 노드를 정한다. **조건부 엣지**는 함수가 상태를 보고 고른다.
- **리듀서(Reducer)**: 같은 키를 여러 노드가 돌려줄 때 합치는 방법.
  - 기본 = **덮어쓰기**
  - `history: Annotated[list[str], operator.add]` = **쌓기**

### 상태는 노드 사이의 계약이고, 조용히 깨진다

| 계약 | 위반 시 |
|---|---|
| Envelope (pydantic, 3강) | **시끄럽게** 에러 → DLQ |
| AgentState (LangGraph) | **조용히** 키를 버리고 계속 진행 |

LangGraph는 `AgentState`에 **선언된 키만** 상태 채널로 만든다. 선언 안 된 키는 START 노드에서 경고 없이 버려진다 (`langgraph/graph/state.py`의 `_get_updates`).

### 실제 버그 — `force_vault_rag` (fix-later 8, 최우선)

- `run_task(force_vault_rag=True)`가 넣은 값이 `AgentState`에 없어 버려진다.
- 그래서 study 모드("키워드 없이 항상 RAG")가 **키워드 없는 질문에서 RAG를 건너뛴다.**
- 증거 3중:
  1. Claude Code 실측: 선언 없으면 노드가 `None`, 한 줄 추가하면 `True`
  2. 실행 history: `route:needs_context:study`가 아니라 `route:needs_context`
  3. Redis `task_status`: study 분기가 남기는 `mode: study` 필드가 **없음**
- 이번 실행이 RAG를 탄 건 질문에 "노트"라는 키워드가 있어서였다.
- `hermes_route_node`의 `force_vault_rag` 분기도 같은 이유로 **도달 불가**.

### 반복과 탈출

- `validate → route` 엣지로 고리가 있다. `max_retries=2`가 탈출 조건인데, 실제로는 **총 2회 시도**다(Claude Code 실측). 실패하면 `error_count`가 0→1(1 ≥ 2 거짓, 재시도)→2(2 ≥ 2 참, 종료)로 오르기 때문이다. 이름은 "재시도 횟수"인데 동작은 "총 시도 횟수"라서 **이름과 동작이 어긋나 있다.** LangGraph 자체 안전장치 `recursion_limit`도 있다(기본 25단계).
- 키워드 라우터는 같은 질문에 같은 경로를 고른다 → 재시도는 **일시적 장애**에만 의미가 있다. 그리고 3강 구멍 B가 이 고리 안에서 벌어진다.

### validate는 생존 확인이다

- 통과 조건: 답 8자 이상 + "error"로 시작하지 않음.
- 환각·모순은 못 잡는다. 실제 사례는 5강 참고. V1.5 계획의 **Critic reflection**이 이 자리를 대신하려던 것.

### 테스트가 초록이라고 안전한 게 아니다

| 테스트 | 확인하는 것 | 이 버그를 잡나 |
|---|---|---|
| 단위 (`route_node` 직접 호출) | 노드 로직 | ❌ LangGraph 필터를 우회 |
| 통합 (컴파일된 그래프에 invoke) | 부품이 **연결됐을 때** | ✅ |

`partial()`로 의존성(store, broker, settings)을 주입해 노드를 테스트하기 쉽게 만든 것은 좋은 설계지만, 그 테스트만으로는 연결의 버그를 못 잡는다.

### 🎯 정확히 알아야 할 것

- LangGraph는 **선언된 키만** 전달한다.
- 리듀서는 키의 **의미**에 따라 고른다.
- 단위 테스트와 통합 테스트는 **다른 버그**를 잡는다.

## 5강. 내 노트를 기억하게 하는 법 — RAG

### 인덱싱 (`pipeline.py:VaultIndexer`)

| 단계 | 방식 | 이유 |
|---|---|---|
| 청킹 (`chunker.py`) | `#`~`###` 헤딩 경계로 자름. `####` 이하는 경계 아님. 첫 헤딩 앞 글은 `(preamble)` | 사람이 쓴 구조를 그대로 경계로 사용 |
| 청크 ID | `파일::헤딩슬러그::순번` — **결정적** | 다시 넣으면 같은 ID로 덮어씀 → 중복 없음 |
| 변경 감지 (`manifest.py`) | **내용 SHA-256 해시** 비교 → added / changed / removed | 수정 시각이 아니라 내용 기준 → 열었다 저장해도 재인덱싱 안 함 |
| 재인덱싱 | 그 파일 청크를 **먼저 지우고** 새로 넣음 | 사라진 헤딩의 고아 청크 방지 |
| 실패 격리 (`index_dlq.py`) | 실패 파일은 `data/index_failures.jsonl`에 기록, 매니페스트 되돌림 | 하나가 실패해도 전체 계속 + 다음에 자동 재시도 |

실행 로그 `+16 ~0 -1 chunks=30`: 새 파일 16개 추가, 사라진 파일 1개 청크 삭제, 총 청크 30개.

### 임베딩

- `nomic-embed-text`(137M, F16): 텍스트 → **768차원** 벡터.
- 뜻이 비슷하면 벡터가 가깝다. 거리는 **코사인**. Chroma가 **HNSW** 인덱스로 근접 이웃을 찾는다.
- 질문도 같은 모델로 벡터가 된다(Chroma가 컬렉션의 embedding function을 자동 적용).
- 임베딩 모델 컨텍스트 **2048토큰**.

### 검색 (`VaultRetriever.search`)

1. 후보 수 `pool = min(max(k×4, k), 20)` → 지금 `.env`의 k=3이면 **12개**
2. Chroma 코사인 검색으로 12개
3. `rerank_hits`로 다시 줄 세워 **3개**
4. 상태에 `retrieved_chunks`(원문 전체), `context_refs`(청크 ID)
5. `build_prompt`: "노트만 근거로 답하고, 없으면 모른다고 하라" + `[1] (파일) 헤딩 본문`
6. study 모드는 답 아래 `Sources:` 인용

**재정렬 규칙 (`rerank.py`)**

| 항목 | 점수 |
|---|---|
| 질문 토큰이 헤딩에 있음 | +3 |
| 본문·파일명에 있음 | +1 |
| `phase N` 파일명 일치 | +8 (데모용 하드코딩) |
| 벡터 거리 | **동점일 때만** |

→ 키워드 점수가 먼저라서 **의미 검색 결과를 키워드가 덮어쓴다.**

### 실제 실행에서 본 것 (TASK-42f5e6b6)

## 6강. 툴을 부르게 하는 법 — Hermes 라우터

### 핵심 개념 — function calling

1. 앱이 모델에게 **툴 정의**(이름, 설명, 인자의 JSON 스키마)를 준다.
2. 모델은 텍스트 대신 **툴 호출 요청**(`tool_calls`: 함수 이름 + 인자)을 낼 수 있다.
3. **앱이** 인자를 검증하고 함수를 실행하고, 필요하면 결과를 모델에게 돌려준다.

→ **모델은 툴을 실행하지 않는다. 실행을 요청할 뿐이다.** 실행 권한과 책임은 앱에 있다.

### MALA에서는 (`src/agents/hermes_router.py`, `src/schemas/tools.py`)

- 툴은 `search_vault` **하나뿐**이다. 인자는 `query`(1자 이상) 하나.
- 툴 스펙을 손으로 쓰지 않고 pydantic 모델(`SearchVaultArgs`)에서 **뽑아낸다**. 그래서 인자를 바꾸면 LLM에 보내는 스펙과 검증 규칙이 함께 바뀐다. 계약의 출처가 하나다.
- `plan_route`: system 프롬프트 + 질문 → `/api/chat`에 `tools=[search_vault]`, `temperature 0`.
- 라우터가 검색까지 끝내면 `retrieved_chunks`가 채워지고, `_route_branch`가 retrieve 노드를 건너뛴다.
- 툴 호출은 **첫 번째 1개만** 처리한다(`tool_calls[:1]`). 결과를 모델에게 다시 돌려주는 반복도 없다. 즉 여러 단계로 툴을 쓰는 에이전트가 아니라 **한 번 판단하는 라우터**다.

**`plan_route`의 갈래**

| 조건 | 결과 | history |
|---|---|---|
| `force_vault_rag` | LLM 생략, 즉시 검색 | `hermes:study_force` — 4강 버그로 **현재 도달 불가** |
| 툴 스텝 ≥ `MAX_TOOL_STEPS`(5) | 서킷 브레이커 → simple | `hermes:circuit_breaker` |
| HTTP 실패 | simple | `hermes:http_fail` |
| `tool_calls` 없음 + vault 단어 있음 + OOD 단어 없음 | **키워드 폴백 검색** | `hermes:no_tool`, `hermes:fallback_search` |
| `tool_calls` 없음 + 그 외 | simple | `hermes:no_tool` |
| `search_vault` 호출됨 | 인자 검증 후 검색 | `hermes:search_vault` |
| 인자 검증 실패 / 모르는 툴 | simple | `hermes:bad_tool_args` / `hermes:unknown_tool` |

폴백은 **OOD를 먼저 본다.** "월드컵"과 "노트"가 둘 다 들어간 질문은 검색하지 않는다.

### 실제로 라우팅을 하는 것은 LLM이 아니라 키워드다

- Phase 4(Ollama 0.24)에서 Hermes의 `tool_calls`가 자주 비어 있었다 → 검색 없이 답 → 환각.
- 키워드 폴백을 넣어 vault 질문의 검색을 **보장**했다.
- 그런데 기록된 성공 사례(`TASK-8f744eba` 등)의 history가 `hermes:fallback_search`다. **툴 호출이 아니라 폴백으로 성공한 것이다.**
- 정리하면 "FC 라우터"라는 이름과 달리, 지금 라우팅을 실제로 수행하는 것은 **키워드 목록**이다.

### 왜 Hermes인가 — 레포에 근거가 없다

- ADR-003에는 **결정만** 있고 "검토한 대안" 항목이 없다.
- `model-comparison.md`에 Hermes 행의 역할이 "8B FC router"라고 적혀 있을 뿐이다. "function calling 특화 모델로 알려져 있다"는 **통념으로 역할을 배정**한 것이다.
- 실측(2026-10-09, Ollama 0.35.1 `/api/show`):

| 모델 | capabilities | 양자화 | 최대 컨텍스트 |
|---|---|---|---|
| hermes3:8b | completion, **tools** | Q4_0 | 131072 |
| qwen3:8b | completion, **tools**, thinking | Q4_K_M | 40960 |

→ qwen3:8b도 tools를 지원한다. "qwen3로 라우팅을 시도해 봤다"는 기록은 없다. 5월 26일 handoff에 "다른 8B FC 모델?"이라는 질문이 열려 있었지만 V1 마감 때문에 보류됐다.

**ADR-001과 대비된다.** ADR-001은 MoE를 VRAM **실측**으로 기각했다. ADR-003은 라우터 모델을 **통념**으로 골랐다. 면접에서 정직하게 말할 지점이고, 바로 다음 실험 주제다.

### 다음 실험 — 라우터 모델 비교

`.env`의 `OLLAMA_ROUTER_MODEL=qwen3:8b` 한 줄만 바꾸면 비교가 된다.

| 측정 | 방법 |
|---|---|
| 툴 호출 성공 | history가 `hermes:search_vault`인지 `hermes:fallback_search`인지 |
| OOD 정확도 | `run_hermes_once --ood`에서 검색하지 않는지 |
| 지연 | 라우팅 단계 시간 |

- 장점: 라우터와 답변 모델이 **같은 모델**이 되면 모델 교체(스왑)가 사라진다. ADR-003의 "동시 상주 금지" 문제 자체가 없어진다.
- 주의: qwen3는 thinking이 기본으로 켜져 있다(fix-later 7). 라우터 호출에도 숨은 추론 토큰이 붙으니 **think 켬/끔 둘 다** 재야 공정하다.
- 결과는 **ADR-004**로 남긴다. 이번엔 "검토한 대안"과 측정 결과를 포함해서.

### 새로 찾은 결함 → fix-later 14~16

- **14. 서킷 브레이커가 사실상 작동하지 않는다.** `tool_step_count`는 검색할 때만 1 늘고 한 라운드에 최대 1번이다. 그래프 시도는 총 2번(실측)이라 `tool_step_count`는 최대 2까지만 오르고, `MAX_TOOL_STEPS=5`에 도달할 수 없다. 다른 장치(`max_retries`)가 항상 먼저 걸린다.
- **15. `_chat`의 JSON 파싱 실패가 처리되지 않는다.** `httpx.HTTPError`만 잡아서 응답이 깨진 JSON이면 예외가 노드 밖으로 터진다.
- **16. 라우터 모델 선택에 측정 근거가 없다.** ADR-003에 대안 검토가 없다.

(사소: `_execute_search`가 `hits_to_chunks`를 두 번 부른다. 결과는 같고 낭비일 뿐.)

### IDPO 논문과 연결

라우터가 입구에서 "검색이 필요한가"를 정하는 구조는 IDPO의 **Intent Gateway**와 같은 모양이다. 그리고 "모델은 요청할 뿐, 앱이 실행한다"는 원리가 툴 권한 보안의 출발점이다. 모델이 무엇을 요청하든 **앱이 검증하고 거부할 수 있어야** 한다. MALA가 인자를 pydantic으로 검증하는 것이 그 최소 형태다.

### 🎯 정확히 알아야 할 것

- function calling에서 **실행하는 주체는 앱**이다.
- MALA의 라우팅은 현재 **키워드 폴백**이 실질적으로 수행한다. "LLM이 툴을 골라 검색한다"고만 말하면 사실과 다르다.
- Hermes 선택은 **측정 근거가 없다**. "FC 특화라고 알려져서"는 근거가 아니다.

| 003 | Hermes 라우터 + 폴백, 두 8B 동시 상주 금지 | 1강, 6강 |

**트러블슈팅 4건 (+ 미작성)**: MoE VRAM · VRAM 측정 불일치 · BIOS/Docker · Ollama 모델 경로(`db.sqlite`가 환경변수보다 우선). Hermes no_tool 건은 인덱스에만 있고 본문 파일이 없다.

### 테스트

- 유닛 테스트 11개 파일, Redis·Ollama 없이 도는 순수 로직(청킹, 라우팅 분기, 매니페스트, 재정렬, 스키마 등).
- `test_manifest.py`와 `test_index_manifest.py`가 같은 함수를 중복 테스트.
- **그래프를 통과하는 통합 테스트가 없다** → 4강 버그를 못 잡은 이유.

### 측정 문화

MALA의 강점은 숫자를 **재서** 결정했다는 것이다: 7,559 / 7,418 MiB, 4096, 5.6GB, 768차원, 약 69초. 면접에서는 "실측했다"와 "추정했다"를 구분해서 말한다.

### 다시 읽기의 가치

V1을 만든 뒤 4개월 만에 다시 읽으면서 13개의 결함을 찾았다. 그중 하나(8번)는 **기능이 조용히 죽어 있었고 테스트는 통과하고 있었다.** 이것 자체가 면접 이야기가 된다: "만들고 끝낸 게 아니라, 다시 읽고 실측으로 확인해 결함 목록을 만들었습니다."

- 테스트의 **층**(단위/통합)이 잡는 버그가 다르다.

## 정답 해설

**1-1.** 두 값은 이미 4비트로 양자화된 상태의 실측이다. 7,418 + 7,559 ≈ 14,977 MiB(약 14.6GB)로 10GB를 넘고, 화면 출력 등으로 약 1GB가 이미 쓰인다. 가중치만 약 5GB + 5GB = 10GB라 KV 캐시와 오버헤드가 들어갈 자리가 없다.

**1-2.** KV 캐시만 커진다(토큰 수에 비례). 가중치와 대부분의 런타임 오버헤드는 그대로다.

**1-3.** 가중치 약 4.9GB(8.2B × 약 4.8비트 ÷ 8) + KV 캐시 약 0.56GB(토큰당 약 144KB × 4096) ≈ 5.5GB.

**2-1.** Ollama가 잠깐 안 받거나 모델을 로딩 중일 때 같은 일시적 실패를 막으려는 것. 해가 되는 경우: ① 404·400 같은 영구 실패까지 재시도한다. ② 타임아웃이 120초라 최악이면 약 366초가 걸리는데 오케스트레이터는 120초만 기다린다 → 늦은 결과가 다음 시도의 답으로 채택되거나 버려진다.

**2-2.** Ollama 서버의 기본값이 정한다. 이 버전에서 실측 4096.

**2-3.** 툴 정의는 chat 형식(메시지 목록)에서만 넣을 수 있기 때문.

**3-1.** 메시지는 `processing_queue`에 남는다. 오케스트레이터는 120초 뒤 `result_timeout`으로 포기하고, validate 실패 → route로 돌아가 **같은 task_id로 새 Envelope**를 넣는다. 갇힌 메시지는 누군가 `requeue_processing`을 호출하기 전까지 그대로 있고, 나중에 되돌리면 같은 작업이 한 번 더 처리된다.

**3-2.** 결과를 공용 `result_queue` 하나가 아니라 **시도별 전용 키**(예: `result:{task_id}:{attempt}`)에 넣고, 오케스트레이터는 자기 키만 `BLPOP`한다. 남의 답을 꺼낼 일이 없으니 A가 막히고, 시도 번호가 다르니 늦은 1차 결과가 2차에 섞이지 않아 B가 막힌다. 키에 만료 시간(TTL)을 걸면 아무도 안 가져간 결과는 자동으로 사라진다.

**3-3.** 같은 메시지가 두 번 처리될 수 있으니, 두 번 처리해도 결과가 한 번 처리한 것과 같아야 한다. 예: 같은 task_id의 결과가 이미 있으면 다시 만들지 않는다.

**4-1.** `retrieved_chunks`가 쌓기면 재시도마다 청크가 누적된다(지금 설정이면 총 2회 시도라 3 → 6개). 프롬프트가 불어나 4096 컨텍스트를 넘고 조용히 잘린다. `history`가 덮어쓰기면 마지막 노드의 기록만 남아 무슨 일이 있었는지 추적할 수 없다.

**4-2.** `build_graph`로 **컴파일된 그래프**를 만든다(inline 모드, 검색과 Ollama 호출은 가짜로 대체). 키워드가 없는 질문("인증 흐름이 뭐야?")과 `force_vault_rag=True`로 `invoke`한다. 결과의 `history[0]`이 `route:needs_context:study`인지 확인한다. 지금 코드에서는 실패해야 하고, `state.py`에 한 줄 추가 후 통과해야 한다.

**4-3.** study 플래그 때문이 아니라 질문에 "노트"라는 단어가 있어서 키워드 라우팅이 `needs_context`를 골랐기 때문.

**5-1.** (일부 추정 — 노트 본문은 확인하지 않았다) 질문 토큰은 "노트", "핵심", "개념", "요약해줘"다. "이"는 한 글자라 토큰 필터(2글자 이상)에서 빠진다. 재정렬이 키워드 우선이라, 헤딩에 "노트"가 있는 청크("공부 노트")가 +3을 받고, 같은 문서의 다른 청크도 본문의 단어로 점수를 얻었을 것이다. 반면 MOC 노트들은 내용이 적어 겹치는 단어가 적었을 가능성이 높다. "이 노트"의 "이"는 검색 시스템에게 **아무 뜻도 없다.** 어떤 노트를 보고 있는지 모르고, 질문을 단어와 벡터로만 다룬다. 지시어가 들어간 모호한 질문은 RAG가 가장 약한 형태다.

**5-2.** 질문, 답변, 검색된 청크를 받아서, 답변의 각 주장이 청크로 뒷받침되는지와 주장끼리 서로 모순되지 않는지를 확인한다.

**5-3.** 검색: 임베딩이 앞 2048토큰만 반영해서 뒷부분 내용으로는 그 청크를 찾을 수 없다. 답변: 일단 검색되면 원문 전체가 프롬프트에 들어간다. 그래서 검색과 답변이 서로 다른 텍스트를 보는 비대칭이 생긴다.

**6-1.** 모델은 툴 정의를 보고 어떤 툴을 어떤 인자로 부를지 **요청**한다. 앱은 그 요청을 검증하고 **실행**하고, 필요하면 결과를 모델에게 돌려준다.

**6-2.** 키워드 폴백만 있으면 vault와 상관없는 질문에도 우연히 vault 단어가 걸려 검색할 수 있다. OOD 목록은 "검색하면 안 되는 질문"을 막는 안전장치다. OOD를 먼저 보는 이유는, 두 종류 단어가 다 있을 때 **검색하지 않는 쪽**을 택하기 위해서다. 잘못된 검색 결과가 들어가면 답이 그럴듯하게 틀리기 쉽다.

**6-3.** 레포에 근거가 없다. "function calling 특화 모델로 알려져 있다"는 통념으로 역할을 배정했고, ADR-003에 대안 검토가 없다. 실제로는 Hermes도 툴 호출에 자주 실패해 키워드 폴백이 라우팅을 수행했다. 확인하려면 라우터 모델만 qwen3로 바꿔 같은 질문 세트(vault 질문, OOD 질문)로 툴 호출 성공 여부(history), OOD 정확도, 지연을 비교한다. qwen3는 thinking 켬/끔 둘 다. 같은 모델을 쓰면 스왑도 사라진다.

**6-4.** `tool_step_count`는 검색할 때만 1 늘고 한 라운드에 최대 1번이다. 그래프는 총 2번 시도하고 끝나므로(실측) `tool_step_count`는 최대 2이고 5에 도달할 수 없다. `max_retries`가 항상 먼저 걸리니 이 장치는 사실상 죽은 코드다.

**7-1.** 일지는 무엇을 했는지 시간순으로 남긴다. ADR은 하나의 결정에 대해 맥락, 고려한 대안, 고른 이유, 그 결과(감수한 비용)를 남기고 상태(제안·채택·폐기)를 갖는다.

**7-2.** 컴파일된 그래프를 통과하는 통합 테스트가 없다. 그래서 노드 단위로는 맞지만 연결됐을 때 깨지는 `force_vault_rag` 버그를 놓쳤다.
